# One-Board Derived Information Model

Status: **Current reference accounting model / experimental**

This document is the authoritative information-accounting model for the current HexDoku experiment.

## 1. Received object

HDE receives exactly one 9×9 Sudoku board containing 25 holes.

~~~text
81 board positions
56 visible cells
25 holes
~~~

The board positions themselves are part of the received array/grid structure.

Therefore HDE does **not** receive a separate list of 25 coordinates.

## 2. Coordinate accounting

A standalone arbitrary cell address among 81 positions needs 7 fixed bits because:

~~~text
2^6 = 64 < 81 <= 128 = 2^7
~~~

Encoding row and column separately with three bits each is insufficient because three bits provide only eight values and a Sudoku axis has nine positions.

However, this standalone-coordinate cost is irrelevant to the current received-board profile.

Given the 81-cell board array, HDE discovers holes by scanning the board:

~~~text
for index in 0..80:
    if board[index] == HOLE:
        record index
~~~

Hence:

~~~text
extra transmitted coordinate bits = 0
~~~

The 25 coordinate identities are derived from the received board.

## 3. Board representation widths

Two simple fixed-width reference encodings are kept distinct.

### Generic 25-hole Sudoku board

Each cell may be:

~~~text
HOLE, 1,2,3,4,5,6,7,8,9
~~~

Ten states require four fixed bits per cell:

~~~text
81 × 4 = 324 bits
~~~

### Fixed 9+9+7 HDC-Lite board

When digits 1 and 2 are always holes and seven of the nine 3s are holes, visible cell states are:

~~~text
HOLE, 3,4,5,6,7,8,9
~~~

Eight states require three fixed bits per cell:

~~~text
81 × 3 = 243 bits
~~~

The 243-bit figure is therefore **specific to the fixed 9+9+7 profile**. It is not the size of every arbitrary 25-hole Sudoku board.

## 4. Information HDE derives without separate transmission

From the received board plus the pinned deterministic rule profile, HDE derives:

1. the 25 hole coordinates;
2. the candidate set at each evaluated coordinate;
3. each HR value;
4. the solved digit for each hole;
5. the deterministic solve/commit order;
6. the canonical alternative-branch slot positions implied by HR.

All of those have zero **additional** transmission cost when exactly reproducible from the board.

~~~text
received board
   |
   +-> hole coordinates
   +-> candidate sets
   +-> HR trajectory
   +-> solved values
   +-> solve order
   +-> branch/reference slot locations
~~~

## 5. Order-space accounting

Twenty-five distinct coordinates have:

~~~text
25!
~~~

possible arbitrary permutations.

The corresponding information-theoretic order-space width is:

~~~text
log2(25!) = 83.681513... bits
~~~

A fixed-width standalone field supporting every possible 25-element order therefore needs 84 bits.

This does not mean the current fixed-order Sudoku-v1 profile carries 83.68 bits. Its E-order is fixed and therefore has zero independent order capacity. The 83.68-bit figure is only the absolute 25-element permutation-space ceiling.

HexDoku does not transmit that 84-bit field in the received-board profile when the order is regenerated deterministically from the board.

However, 83.68 bits is only the **absolute permutation-space ceiling**.

If the HDC/HDE rules can realize only K distinct solve orders from the supported board family, actual independent order-channel capacity is:

~~~text
log2(K) bits
~~~

and may be much smaller than 83.68 bits.

## 6. What compression has actually occurred?

Consider a baseline that sends both:

~~~text
board + standalone order field
~~~

and compare it with HexDoku's:

~~~text
board only; order regenerated by HDE
~~~

If the full 25! order space is genuinely realizable:

### Fixed 9+9+7 board

~~~text
baseline = 243 + 83.6815 = 326.6815 bits
HexDoku  = 243 bits
saved    = 83.6815 bits
reduction ≈ 25.62%
~~~

### Generic four-bit-cell board

~~~text
baseline = 324 + 83.6815 = 407.6815 bits
HexDoku  = 324 bits
saved    = 83.6815 bits
reduction ≈ 20.53%
~~~

If only K solve orders are reachable, replace 83.6815 by `log2(K)`.

If K=1, order-derived compression is 0%.

Therefore the guaranteed order-channel gain is not claimed until K is measured.

## 7. HR branch-reference accounting

At an evaluated coordinate:

~~~text
HR = candidate_count - 1
~~~

If one anchor candidate is implicit:

~~~text
alternative branch/reference slots = HR
~~~

HDE can regenerate the **positions and ordering of these slots** from the board and rule profile, so separate branch-position metadata can be omitted.

But the reference values themselves are not free.

A hash/object ID/reference must still be transmitted, already shared, or retrievable from a shared manifest/dictionary.

Thus HexDoku may remove:

~~~text
where does this reference belong?
~~~

metadata, but it does not make an unknown referenced object appear from its hash.

## 8. HDE computational target

The lightweight HDE target rejects or falls back from boards requiring uncontrolled backtracking.

For a no-backtracking 25-hole path, a simple implementation may scan the remaining holes at each stage.

Maximum cell evaluations:

~~~text
25 + 24 + ... + 1 = 325
~~~

A cell evaluation can be implemented with three 9-bit mask loads plus a small number of OR/AND/invert/popcount/test operations.

Therefore the intended reference cost is:

~~~text
325 candidate-cell evaluations
+ one 81-cell input scan
+ 56 visible-cell mask inserts
+ 25 commits
~~~

which is expected to translate to a few thousand simple integer/bit operations.

This is an implementation target, not a measured CPU-instruction result.

If exact feasibility/backtracking is required, the operation count is not bounded by this small estimate. HDC-Lite should prefer boards that stay on the no-backtracking path.

## 9. Comparison with a conventional 84-bit permutation field

A conventional 84-bit permutation rank can be expanded with a factoradic decoder.

A simple implementation needs roughly:

~~~text
24 div/mod steps
+ 25 selections
+ up to ~300 simple element moves in an array implementation
~~~

HexDoku trades that explicit 84-bit order field for extra Sudoku-derived computation.

The engineering trade is therefore:

~~~text
conventional:
    board + order bits
    cheaper order decoding

HexDoku:
    board only
    more reconstruction work
    no separate order field when the order is derivable
~~~

## 10. Current claim boundary

The current defensible claim is:

> A received 25-hole Sudoku board can implicitly determine its hole coordinates, solution values, deterministic reconstruction order, HR trajectory, and HR branch-slot positions, eliminating separate transmission of those derived metadata fields.

The current project does **not** yet claim that:

- every one of the 25! solve orders is reachable;
- 83.68 independent payload bits are guaranteed;
- every HR slot is independent payload capacity;
- HexDoku universally beats conventional compression.

Those claims require measured K, HR distributions, packet sizes, and HDE runtime.

## 11. Required one-board measurements

For each test board record:

- received board width;
- generic or 9+9+7 profile;
- exact 25 hole coordinates;
- reconstructed values;
- deterministic solve order;
- order identifier/rank for analysis only;
- distinct reachable-order count K across HDC choices;
- `log2(K)`;
- HR histogram;
- `sum_hr_targets` and `sum_hr_dna`;
- branch-reference slot count and deduplicated reference count;
- HDE candidate-cell evaluations;
- HDE measured CPU instructions/cycles when instrumentation is available;
- exact final Parity equality.

## 12. Fixed-order baseline versus order-bearing profile

The project now distinguishes two meanings of "order":

### Baseline `sudoku-v1`

`E0..E24` is fixed once in row-major hole order and HR/q never reorders it.

Therefore, relative to E identities:

~~~text
K = 1
independent order capacity = 0 bits
~~~

The fixed order can still be omitted from the packet because both endpoints know the rule, but this is metadata omission, not an information-bearing order channel.

### Experimental `sudoku-order-bearing-mrv-v0`

The next coordinate is selected dynamically by:

~~~text
minimum candidate count (minimum HR)
then row-major tie-break
~~~

so different valid received boards may produce different derived 25-coordinate orders.

For one fixed Parity and the 36-mask `9+9+7` HDC family, `K <= 36`, so capacity can never exceed `log2(36) ≈ 5.17` bits in that restricted experiment.

The current single-Parity reference sample measured:

~~~text
accepted masks = 27 / 36
K = 27
log2(K) ≈ 4.7549 bits
~~~

To approach the absolute `log2(25!) ≈ 83.68`-bit permutation ceiling, the HDC construction family itself must expose at least 25! distinguishable valid board/order outcomes. The current 36-mask family cannot do that.

See [ORDER_BEARING_PROFILE_V0.md](ORDER_BEARING_PROFILE_V0.md).

## 13. 500-board measured boundary

The fixed 36-mask `9+9+7` family was tested on 500 generated completed Sudokus, all 36 masks per board:

~~~text
18,000 mask evaluations
3,780 exact round trips
367 boards with >=1 valid mask
133 boards with NO_MASK
~~~

For the experimental dynamic order-bearing profile:

~~~text
K over all boards: min=0, mean=7.56, median=6, max=30
successful-board mean log2(K) = 2.9280 bits
maximum measured log2(K)      = 4.9069 bits
~~~

Therefore:

~~~text
current guaranteed independent order capacity = 0 bits
~~~

The fixed baseline can still omit a known deterministic order field as metadata, but the current 36-mask family does not guarantee a selectable variable-order payload.

To obtain a guaranteed non-zero order channel, HDC must expand its construction family and enforce a minimum-K acceptance rule.

See [ORDER_HR_CORPUS_500.md](ORDER_HR_CORPUS_500.md).
